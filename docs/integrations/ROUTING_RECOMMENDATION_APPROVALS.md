# AI Films Routing Recommendation Approval Ledger

Gate 16 adds a durable human-governance layer between Gate 15 routing recommendations and any future runtime policy change.

## Purpose

A routing recommendation is still advisory. A human operator may now approve or reject the exact evidence snapshot that produced the recommendation, but that decision does not change provider configuration, activation state, canary state, dispatcher scoring, job queues, or provider spend.

## Persistence

The staging schema adds `public.ai_film_routing_recommendation_approvals` with:

- owner and reviewer identity derived from the active authenticated Supabase session;
- project scope when available;
- recommendation key, provider, optional visual style, action, bounded proposed adjustment, and confidence;
- explicit `approved` or `rejected` decision;
- required human rationale;
- complete recommendation evidence JSON;
- server-generated SHA-256 evidence hash;
- decision and creation timestamps.

The uniqueness contract is `(owner_id, recommendation_key, evidence_hash)`, so the same exact recommendation evidence cannot be decided twice while later evidence for the same provider/style can receive a new human decision.

## Security model

RLS is enabled. Anonymous access is revoked. Authenticated users receive only `SELECT` and `INSERT`; they cannot update or delete approval records. Separate RLS policies restrict reads and inserts to the signed-in owner, and the database defaults both owner and reviewer identity from `auth.uid()` so the browser does not submit user identity fields.

The evidence hash is generated by a `SECURITY INVOKER` trigger before insert. No service-role credential is exposed to the browser.

## Operator workflow

`RoutingRecommendationWorkspace` now:

1. generates Gate 15 evidence-qualified recommendations;
2. loads existing owner-scoped approval records;
3. matches decisions only to the exact current recommendation evidence;
4. requires a human rationale;
5. records either `approved` or `rejected`;
6. shows the immutable decision, evidence hash, and timestamp;
7. keeps the runtime unchanged.

The interface intentionally says **Approval ≠ apply**. There is no Apply action in Gate 16.

## Deployment boundary

The Gate 16 migrations were applied only to the existing staging Supabase project during implementation. No production Supabase migration was applied. PR #1191 remains unmerged. Replicate remains blocked behind its separate protected paid certification canary and runtime activation flags.

## Next gate

A future gate may add a separate, protected promotion contract that consumes an approved recommendation and produces a reviewable runtime-policy change request. That contract must remain distinct from the approval ledger and must not bypass provider activation/canary requirements.
