## Rollback baseline

Rollback should return the frontend and backend to the deployments associated with the certified commit above, while preserving production database state unless a database-specific rollback is explicitly approved.

Before rollback:

1. Capture the failing deployment identifier and timestamps.
2. Preserve Railway, Vercel, Sentry, and application logs.
3. Confirm whether the incident is frontend-only, backend-only, provider-specific, or database-related.
4. Avoid rotating working OpenAI, Pinecone, Supabase, Resend, or Redis credentials unless credential failure is confirmed.
5. Re-run health, authentication, Chat/RAG, and contact-form canaries after rollback.

- the commit and deployment IDs;
- the affected services;
- required migration or provider changes;
- rollback instructions;
- post-deploy canary evidence.
